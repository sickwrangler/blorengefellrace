# Phase 3C.1B production CLOSED deployment runbook

Status: prepared for review only. It is not authority to provision, deploy, configure providers, invite runners or change registration state.

## Required manual inputs

Record approval for: globally unique naming suffix; production resource-group name; Azure subscription; alert and budget recipients; named organiser identities; Static Web Apps Free-plan acceptance; under-18 launch-gate value (remain false until WFRA confirmation); backup retention; transactional sender choice; future email domain; Stripe live account and statement details; support contact; maintenance window; deployment approver; rollback owner.

Secret values must be entered only into Azure/Stripe configuration at the relevant gate and must never be pasted into issues, logs, chat, command history or repository files.

## Retention direction pending final approval

Emergency-contact data is temporary operational safety information. Raw addresses are retained only as long as needed for event administration and carbon analysis; derived anonymised environmental information may be kept longer. Financial and refund audit records currently have a proposed seven-year record-keeping period, while historical race results are long-term race records. Email addresses and phone numbers are not retained or used for marketing. Final deletion windows must be approved before public `OPEN`; this phase adds no irreversible retention automation.

## Gate 1 — review and merge

1. Review the exact 66-file web, 18-file API and 17-file scheduler manifests generated by the staging scripts.
2. Confirm all validators, tests, dependency audits, secret scan and production simulation pass from the proposed main commit.
3. Review the production adapter, role rules, CLOSED bootstrap and IaC diff.
4. Merge only after approval. Do not install or execute the proposed production workflow yet.

Rollback: abandon or revert the un-deployed code change. Production remains on its existing 45-file artifact.

## Gate 2 — provision isolated resources

1. Create or select the approved production resource group in West Europe.
2. Run an Azure Bicep validation/what-if for `infrastructure/registration-production/main.bicep`; confirm it does not reference development resources or modify the existing Static Web App.
3. Deploy the approved template with manually supplied suffix and alert recipients.
4. Deploy the separately reviewed subscription budget.
5. Verify public blob access is disabled, blob versioning/soft delete is enabled, Table and containers exist, the scheduler identity is unique and role scopes are limited.

Rollback: delete only newly created, still-empty production-registration resources after preserving the deployment record. Never touch the existing production Static Web App or development resource group.

## Gate 3 — configure the production API while providers remain disabled

Configure the managed production API using these setting names only: `REGISTRATION_ENVIRONMENT`, `REGISTRATION_STORAGE_ACCOUNT`, `REGISTRATION_TABLE`, `REGISTRATION_TABLE_SAS_TOKEN`, `REGISTRATION_EVENT_PARTITION`, `REGISTRATION_PUBLIC_BASE_URL`, `REGISTRATION_UNDER18_ENABLED`, `REGISTRATION_MAX_RUNNERS_PER_ORDER`, `STRIPE_ENABLED`, `ACS_EMAIL_ENABLED`. Set environment to production, the public URL to the custom production origin, under-18 false, Stripe false and ACS false. Do not set a deployment-controlled OPEN state.

Create a revocable Table-only SAS with the shortest practicable validity and store it only as an application setting. Validate that all resource names contain the production naming convention and none contains development/test identifiers.

Rollback: revoke the SAS and remove only the new registration app settings. Existing public pages remain available.

## Gate 4 — deploy the CLOSED application

1. Install/approve the proposed workflow only after deciding how it replaces the existing 45-file workflow without a later public-site deployment reverting registration.
2. Require the protected `registration-production` GitHub environment approval.
3. Build the explicit artifacts from `main`; compare their manifests with the review record.
4. Deploy the web/API artifact. Deploy the scheduler package separately to the new Function App.
5. Do not run a state transition.

Rollback: keep the scheduler disabled and redeploy the last compatible artifact. Do not revert to the public-only artifact after secure links or Stripe events exist without a webhook-preservation plan.

## Gate 5 — verify CLOSED bootstrap and boundaries

Verify environment production, state CLOSED, capacity 120, prices £6/£4, under-18 gate false and every business collection empty. Missing/malformed state must return CLOSED/unavailable. Confirm runner order creation is rejected, start list is empty, development/test routes are 404, and anonymous or merely authenticated dashboard/API access is denied.

Rollback: disable registration API routes or redeploy the previous artifact; preserve the newly created store for investigation.

## Gate 6 — organiser authorization

1. In the production Static Web App, invite each approved named organiser to the literal role `organiser` using Azure/Static Web Apps role management.
2. Sign out/in and verify the dashboard plus `/api/v2/organiser/*`, `/api/v3/organiser/*` and `/api/v4/organiser/*` behavior.
3. Verify anonymous access and an authenticated user without `organiser` are denied server-side.
4. Record who approved each assignment and its planned review/removal date. Do not hard-code identities.

Rollback: revoke the role assignments. Do not weaken route rules.

## Gate 7 — backups, scheduler and monitoring

Create a pre-launch snapshot and validate its checksum. Exercise restore once with isolated synthetic production-like data while CLOSED. Bind the prepared backup policy so the first scheduler run at or after 02:00 UTC creates one snapshot per UTC day only while `PRIVATE_LIVE`, `OPEN` or `PAUSED`; keep pre-launch, pre-race and before-significant-change snapshots as explicit operator actions. Do not enable automatic backup deletion. Confirm scheduler identity access, harmless CLOSED execution, 30-minute heartbeat, backup visibility, 30-day privacy-minimal telemetry and focused alerts. Confirm logs contain no form payloads, contact data, tokens or webhook bodies.

Rollback: disable the scheduler, retain snapshots and correct role/configuration errors while CLOSED.

## Gate 8 — provider configuration (later explicit approvals)

Stripe: configure live key and signing secret only in application settings, create `/api/v3/stripe/webhook` for the six reviewed event types, test signature rejection and reconciliation, then explicitly set `STRIPE_ENABLED=true`. Never use sandbox keys in production.

Email: initially an Azure-managed sender may be used for controlled validation if approved. Before real runner messages, verify the chosen race-domain ownership TXT, SPF and two DKIM records, link the domain, configure the approved sender and explicitly set `ACS_EMAIL_ENABLED=true`. Never configure a safe-recipient redirect in production.

Rollback: disable the affected provider flag. Preserve webhook/payment state; do not delete records or automatically refund.

## Gate 9 — final CLOSED smoke test

Repeat artifacts, access, empty-state, scheduler, backup, monitoring, provider-disabled/enabled-as-approved and public-page checks. Registration must remain CLOSED. Record commit, deployment IDs, resource inventory and evidence.

Rollback: return to the previous gate while retaining the store and financial audit records.

## Gate 10 — Phase 3D approval only

After external WFRA confirmation, legal/privacy wording approval and provider verification, request separate authority for Phase 3D. An organiser must use the authenticated state endpoint with the expected current state and explicit confirmation to move `CLOSED` to `PRIVATE_LIVE`. A deployment, date, URL, invitation or app setting must never perform that transition. Do not create invitations before that approval.
