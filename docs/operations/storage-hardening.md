# Production storage limits and headroom

## Contract

Production stores one compressed, Base64-encoded event state in one Azure Table entity. The API and external scheduler share `production-storage-codec.mjs`; both use 30,000-character chunks.

Microsoft documents a 64 KiB maximum string value, a 1 MiB aggregate entity limit and 255 properties including `PartitionKey`, `RowKey` and `Timestamp`. Because Table strings are UTF-16, this application keeps each property below 32,000 characters and stops before a deliberately conservative 768 KiB estimated entity ceiling. The estimator includes UTF-16 names/values and conservative per-property overhead. See [Microsoft's Table data model](https://learn.microsoft.com/en-us/rest/api/storageservices/understanding-the-table-service-data-model).

| Conservative 768 KiB ceiling used | Level | Operator response |
|---:|---|---|
| below 60% | Healthy | Normal monitoring |
| 60–74.99% | Information | Review retained-history growth |
| 75–84.99% | Warning | Plan/accelerate migration and reduce unnecessary retention |
| 85–99.99% | Urgent | Pause before further material growth unless reviewed evidence says safe |
| 100% or a property/count limit | Blocked before Azure write | Treat as an incident; do not bypass the guard |

Successful writes emit only chunk count, encoded-character count, largest chunk, UTF-16 estimate, entity estimate, property count, headroom percentage and level. Failures emit only operation/error category, status and those aggregates. State JSON, runner data, contact details, tokens and payment details must never enter telemetry.

The organiser-only `/api/v2/organiser/storage-metrics` endpoint reads the entity inside the managed API and returns only aggregate measurements. It must remain protected by the literal `organiser` role; never add chunk values to its response.

## Synthetic lifecycle forecast

Generated by `node scripts/forecast-registration-storage.mjs` using synthetic-only, production-shaped data:

| Scenario | Compressed bytes | Base64 chars | Chunks | Largest chunk | Estimated entity | Properties | 768 KiB use |
|---|---:|---:|---:|---:|---:|---:|---:|
| 18 active | 8,392 | 11,192 | 1 | 11,192 | 23.7 KiB | 9 | 3.08% |
| 60 active | 24,077 | 32,104 | 2 | 30,000 | 64.7 KiB | 10 | 8.42% |
| 100 active | 38,921 | 51,896 | 2 | 30,000 | 103.3 KiB | 10 | 13.45% |
| 120 active | 46,474 | 61,968 | 3 | 30,000 | 123.1 KiB | 11 | 16.03% |
| 120 plus lifecycle history | 66,632 | 88,844 | 3 | 30,000 | 175.6 KiB | 11 | 22.87% |

The history scenario includes multi-runner orders, payments, declarations, communications, audits, amendments, race-number events, transfers, refunds, expired Checkouts, waiting-list entries/offers, revoked tokens and retained provider/event evidence. It is intentionally realistic rather than a pristine 120-runner list.

On this evidence the one-entity design is **Comfortable for 2026**, provided telemetry and manual snapshots remain active. The lifecycle forecast uses less than one quarter of the conservative ceiling and 17.2% of Azure's documented 1 MiB limit. It remains a serialization/throughput hotspot and is not the recommended long-term design.

Future migration direction: separate event/config and capacity-ledger entities from runner, registration, order, payment/reconciliation, communication/audit and public-projection entities. Design that migration after the 2026 live cycle; do not migrate the active production state as part of an incident response.

## Validation commands

```sh
node scripts/forecast-registration-storage.mjs
node --test tests/registration-production-storage.test.mjs
```

The manual development Azure proof is `api/scripts/prove-development-table-storage.mjs`. It requires the explicit `SYNTHETIC_ONLY` guard and development SAS settings supplied only in the process environment. It refuses resource names that do not contain `dev` or `test`, creates UUID-scoped synthetic partitions, verifies multi-chunk read/Replace and 10-/20-way ETag concurrency, then deletes its entities. Never pass production settings to it and never put credentials in shell history or documentation.
